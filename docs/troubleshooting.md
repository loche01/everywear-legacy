# 주요 트러블슈팅

프로젝트 종료 후 복구·개선 과정에서 원인 분석과 구조 변경이 필요했던 항목을 정리합니다.

## 1. 작업본마다 다른 DB 구조와 DAO

### 문제

팀 프로젝트가 끝난 뒤 남은 작업본들은 서로 버전이 달라, 어느 것을 골라도 DB와 코드가 맞지 않아 실행되지 않았습니다.

### 원인

팀원별로 작업하던 코드가 한 번에 합쳐지지 않았고, 원본 schema(`TABLE.sql`)와 각 작업본의 DAO가 기대하는 테이블·컬럼이 달랐습니다. 여러 DAO가 `SELECT *` 결과를 컬럼 순서로 읽고 있어 컬럼 순서까지 맞아야 했습니다.

### 해결

- 가장 완성도가 높은 작업본을 기준으로 삼았습니다.
- DAO의 `SELECT`, `INSERT`, `UPDATE`, `DELETE`를 기준으로 필요한 테이블·컬럼과 순서를 대조했습니다.
- 원본 schema는 수정하지 않고, 기능 영역별 복구 SQL 9개로 나눠 다시 작성했습니다.
- DB 접속 정보는 코드에서 빼고 환경변수로 받도록 바꿨습니다.

### 결과

빈 MySQL에 공개된 SQL만 순서대로 적용하면 설치되고, 로그인·상품·장바구니 등 주요 기능이 동작합니다. 설치 순서는 [DB 복구와 데이터 구분](db-recovery.md)에 정리했습니다.

## 2. Java 21에서 인증 메일이 발송되지 않음

### 문제

관리자 로그인, 비밀번호 재설정 등 인증번호 메일이 전혀 발송되지 않았습니다.

### 원인

프로젝트에 포함된 JavaMail 1.4.6이 Gmail SMTP에 STARTTLS로 연결할 때 TLS 1.0을 사용했습니다. Java 21은 TLS 1.0을 기본으로 막기 때문에 연결 단계에서 실패했습니다.

### 해결

`GmailSend`의 SMTP 설정에 `mail.smtp.ssl.protocols=TLSv1.2`를 지정했습니다.

### 결과

관리자 이메일 인증번호가 실제 메일로 수신되는 것을 확인했습니다.

## 3. 클라이언트가 보낸 결제 금액을 그대로 저장

### 문제

원본 결제 완료 처리는 브라우저가 보낸 결제 금액과 결과를 서버에서 다시 확인하지 않고 주문·결제 데이터로 저장했습니다. 금액을 조작해도 주문이 완료되는 구조였습니다.

### 원인

결제창의 결과를 그대로 신뢰했고, PG사에 실제 결제 금액을 다시 조회하는 서버 검증 과정이 없었습니다.

### 해결

- 먼저 결제 경로 전체를 막아 주문·결제·배송 저장, 적립금 변경, 결제 후 장바구니 삭제, 문자 발송을 제거했습니다.
- 이후 원본과 같은 아임포트 테스트 식별코드와 이니시스 테스트 결제창까지만 되살렸습니다.
- 결제 결과는 화면에만 보여 주고 DB에는 저장하지 않습니다.
- 주문자 입력값은 `JSONObject.quote`로 escape하고, 결제 금액은 1원 이상 1천만 원 이하 정수만 허용합니다.

### 결과

결제 흐름은 테스트 결제창까지 보여 줄 수 있고, 금액 위조로 주문이 만들어지는 경로는 없습니다. 실제 저장까지 하려면 서버에서 PG사에 금액을 다시 확인하는 과정이 필요하며, 이 부분은 구현하지 않았습니다.

## 4. 카카오 로그인에서 이메일을 받을 수 없음

### 문제

카카오 로그인 후 예외가 나고 404 화면으로 이동했습니다. 예외를 고친 뒤에도 이메일이 없어 회원을 식별할 수 없었습니다.

### 원인

- 동의항목이 설정되지 않으면 응답에 `kakao_account`가 없는데, 코드는 항상 있다고 보고 파싱했습니다.
- 실패 시 존재하지 않는 `error.jsp`로 이동했습니다.
- 카카오는 개인 개발자 앱에 이메일을 제공하지 않습니다. 이메일을 받으려면 비즈 앱 전환과 심사가 필요합니다.

### 해결

- 응답을 안전하게 파싱하고, 실패 시 로그인 화면에 안내를 표시하도록 바꿨습니다. 구글도 같은 방식으로 정리했습니다.
- 모든 앱에 항상 제공되는 카카오 회원번호(`kakao_<id>`)로 회원을 식별하고, 이메일은 있을 때만 부가 정보로 씁니다.
- REST API 키의 클라이언트 시크릿을 토큰 요청에 포함했습니다.

### 결과

실제 카카오 계정으로 로그인해 회원번호와 닉네임을 받고, 가입된 계정은 메인 화면으로 이동하는 것을 확인했습니다.

## 5. 평문 비밀번호를 해시로 옮기기

### 문제

비밀번호가 평문으로 저장되어 있었습니다. 해시로 바꾸려면 기존 계정의 비밀번호를 알아야 했습니다.

### 원인

해시는 되돌릴 수 없어서, 기존 평문 값을 한 번에 해시로 바꾸면 이후 로그인 비교 방식과 섞여 혼란이 생깁니다.

### 해결

- PBKDF2WithHmacSHA256(600,000회, 사용자별 salt)으로 저장하고, 저장값에 알고리즘과 반복 횟수를 함께 기록했습니다.
- 로그인 시 저장값이 해시 형식이면 해시로 비교하고, 평문이면 평문으로 비교한 뒤 성공하면 그 자리에서 해시로 바꿉니다.
- 신규 가입·비밀번호 변경·재설정은 처음부터 해시로 저장합니다.

### 결과

기존 계정은 비밀번호를 다시 설정하지 않아도 첫 로그인에서 해시로 전환됩니다. 신규 설치 계정으로 이 전환을 확인했습니다.

## 6. 사이즈가 없는 상품 314개

### 문제

원본 상품 1,518개 중 314개가 사이즈 정보가 없어 장바구니에 담을 수 없었습니다.

### 원인

당시 사이즈를 상품 설명의 `S - Length ...` 표기에서 정규식으로 뽑았습니다. 설명에 이 표기가 없는 상품은 사이즈가 빠졌습니다.

### 해결

당시 이 상품들의 상세 페이지 SIZE 옵션을 다시 크롤링해 둔 결과를 찾아, 별도 SQL(`original_product_detail_supplement.sql`)로 만들었습니다. 사이즈 표기는 쇼핑몰 옵션명 그대로 두었습니다.

### 결과

transaction 안에서 적용해 확인한 결과, 사이즈 없는 상품이 314개에서 10개로 줄었고 상위 상품이 없는 행은 0건이었습니다. 크롤링 과정은 [상품 데이터 크롤러](../crawler/README.md)에 정리했습니다.

## 7. 원본 카테고리 데이터에 최상위 분류가 없음

### 문제

관리자 상품 관리 화면의 카테고리 선택 목록이 비어 있었습니다.

### 원인

화면은 최상위 카테고리(`top_category IS NULL`)부터 불러오는데, 원본 카테고리 데이터에는 최상위 행이 없었습니다.

### 해결

원본 데이터는 그대로 두고, `CategoryDAO.getTopCategories()`가 하위 카테고리의 `top_category` 값에서 최상위 목록을 만들도록 바꿨습니다.

### 결과
